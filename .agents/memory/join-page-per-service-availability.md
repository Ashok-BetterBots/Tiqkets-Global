---
name: Customer join page — per-service availability
description: How the QR/link queue-join page decides open/closed, and why it is per-service not branch-wide.
---

The customer queue-join page (GET `/api/join/:branchId` → `server/templates/join-queue.html`) must evaluate availability **per service**, not branch-wide.

**Rule:** each active service gets its own `availability` from `getBranchAvailability(branchId, now, service.id)` (honors the service's own operating hours / holidays / breaks with branch fallback, plus the branch `scheduleOverride`). The service's manual `queueStatus` (Booking Open/Paused/Closed) is layered on the client. Only two conditions block the WHOLE branch on this page: branch deactivated (`closed_inactive`) and staff manual branch pause/end (use `manualQueueStatus`, the raw `branch.queueStatus` — NOT the hours-derived `branchQueueStatus`/`effectiveQueueStatus`, which is `ended` whenever branch default hours are closed and would falsely hide everything).

**Why:** branch default schedule is just a fallback; a service can set its own hours. Previously the page computed one branch-level availability with no `serviceId`, so a service open today via its own override was hidden whenever the branch's default day was closed. It only "worked" when `scheduleOverride` was ON (override makes `getBranchAvailability` ignore hours and return open).

**How to apply:** client `enabledEntries` must contain only truly joinable services — a service is joinable iff its schedule state is `open`/`on_break` AND its `queueStatus` is active. Auto-skip to the form only when the branch has exactly one active service and it is joinable; branches with multiple active services must keep the picker visible even if only one is currently enabled. POST `/api/join` already gates per-service via `getBranchAvailability(..., serviceId)` + service `queueStatus`; keep GET and POST consistent.

**Branch/service/desk queueStatus must stay in sync in both directions.** Branches seed with `queueStatus: "ended"` by default. The branch PUT cascades "active" down to services still sitting in that untouched "ended" default (branch→service, pre-existing). The reverse also matters: if staff open booking scoped to a service or desk (not the whole branch) in the dashboard/mobile, only that service/desk flipped active while the branch stayed "ended" — and since this page's own-branch block (`closed_inactive` / manual branch pause-end) reads raw `branch.queueStatus`, customers saw a false "Queue is closed" banner even though the service itself was open and within hours. Fix: `PUT /api/dashboard/services/:id/queue-status` and `PUT /api/dashboard/desks/:id/queue-status` also cascade upward (service/desk→branch, and desk→service) when setting "active" and the parent is still the untouched "ended" default — never overriding an explicit "paused" branch. Client-side optimistic state (`OrganizationContext.setQueueStatusFor`, `dashboard.html setQueueStatus`) must mirror the same upward cascade so the branch-level toggle UI doesn't lag behind until next refetch.
