BUG: Ticket-call audio announcement currently stops/fades when the app 
is backgrounded (e.g., user presses Home). It should continue playing 
in the background, since this is the entire purpose of our declared 
UIBackgroundModes: audio entitlement for iOS.

SCOPE — READ CAREFULLY:
This fix is ONLY about making the existing audio-announcement feature 
continue playing when backgrounded. Do not touch:
- Any other notification behavior (push notifications, badges, banners)
- The foreground audio playback logic/trigger itself — only how it 
  behaves once backgrounded
- Any other screen, navigation, or feature
- Android behavior, unless the same root cause applies there too — 
  confirm before changing Android code

INVESTIGATION FIRST (report back before fixing):

1. Locate exactly where the ticket-call audio is triggered and played 
   — likely in client/services/NotificationService.ts and/or wherever 
   the queue-status event is received. Report which audio library is 
   in use (expo-av, expo-audio, or a native module).

2. Check the current audio session/mode configuration. Specifically:
   - Is the audio category set to something backgroundable (iOS 
     requires the session category to be "Playback", not "Ambient" or 
     "SoloAmbient" — ambient categories are muted when the app 
     backgrounds by design)
   - Is `staysActiveInBackground: true` (or the equivalent option for 
     whatever library is in use) actually set on the audio mode config?
   - Is this audio-mode configuration applied globally at app startup, 
     or only within the screen/component where the sound plays? If 
     it's scoped to a component that unmounts on background, that's 
     likely the root cause.

3. Check HOW the ticket-call event reaches the device while 
   backgrounded — is it via a push notification (which can trigger 
   background code via a notification handler), a persistent 
   WebSocket/polling connection, or something else? This matters 
   because if the trigger itself doesn't fire while backgrounded 
   (regardless of audio config), the audio can't play at all — that 
   would be a different, larger issue to flag separately, not silently 
   patch.

Report findings before implementing anything.

FIX (only after investigation confirms root cause):

- Set the correct backgroundable audio session category/mode 
  (`playsInSilentModeIOS: true`, `staysActiveInBackground: true`, 
  and category "Playback" — adjust exact option names to whatever 
  library is confirmed in use) at app initialization level, not scoped 
  to a single screen, so it persists regardless of navigation state.
- Ensure this configuration does not force ALL app audio (if any other 
  audio exists elsewhere in the app) into a different behavior than 
  intended — scope the fix to the ticket-announcement sound path 
  specifically if the audio library allows per-sound configuration, 
  otherwise flag if a global audio-mode change is unavoidable.
- Do not change the volume, sound file, trigger condition, or any 
  visual/UI element tied to this feature.

TESTING REQUIREMENT:
This must be verified on a physical iOS device, not simulator, since 
background audio behavior differs from simulator behavior. After the 
fix:
1. Confirm the announcement still plays correctly in the foreground 
   exactly as before (no regression)
2. Confirm it now continues playing after backgrounding the app 
   (Home button / app switcher) before the event fires
3. Confirm no other notification, alert, or feature behavior changed

Report every file touched and the specific config values changed.
